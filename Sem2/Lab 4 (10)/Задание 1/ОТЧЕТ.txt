1. Формулировка проблемы

Большие языковые модели за последние пару лет перестали быть чем-то, что живёт только в облаке: их можно скачать и запустить на обычном ноутбуке. Открытым остаётся вопрос, насколько маленькая локальная модель — на 3 миллиарда параметров, помещающаяся в 6 ГБ видеопамяти — пригодна для реальной прикладной задачи, а не для красивой демонстрации. Моя задача по варианту: приложение, которое запрашивает прогноз погоды через публичный API, передаёт данные локальной LLM и выводит пользователю структурированный совет — какую одежду выбрать, брать ли зонт.

Задача только звучит просто. Во-первых, маленькие модели плохо держат формат ответа: просишь чистый JSON — получаешь JSON, обёрнутый в поясняющий текст, или JSON с выдуманными полями, а приложению этот ответ нужно программно разобрать и красиво отрисовать. Во-вторых, у локальной модели нет «характера» из коробки: чтобы она стабильно играла роль синоптика и придерживалась правил (зонт — по осадкам, крем — по УФ-индексу), её нужно под роль настраивать. В-третьих, модель регулярно ошибается — и в решениях, и в лексике, — поэтому вокруг неё нужна обвязка, которая ошибки ловит и компенсирует. По сути работа — про проектирование такой обвязки вокруг маленькой модели.

Отдельная практическая задача по варианту — оценить рынок бесплатных ИИ-ассистентов: вся разработка велась с использованием бесплатного ИИ, и по итогам нужно понять, где проходит граница возможностей бесплатного сегмента при закрытии реальных задач разработки.

2. Анализ существующих подходов

Источник погоды. Классический вариант из условия — OpenWeatherMap, но его бесплатный тариф требует регистрацию и API-ключ, который неудобно таскать в учебном проекте. Альтернативы без ключа: wttr.in (симпатичный, но это скорее консольная игрушка с нестабильным аптаймом) и Open-Meteo — полноценный прогнозный API с геокодингом, без регистрации, с честной лицензией для некоммерческого использования. Выбрал Open-Meteo: два запроса (геокодинг города и прогноз с текущей погодой, суточными минимумами/максимумами, вероятностью осадков, ветром и УФ-индексом) полностью закрывают потребности советника.

Запуск локальной модели. Основных инструментов три: llama.cpp (максимальный контроль, но всё делается руками), LM Studio (удобный графический интерфейс, но закрытый код и слабые возможности автоматизации) и Ollama (открытый код, REST API из коробки, менеджер моделей и механизм Modelfile). Приложению нужен программный доступ к модели, поэтому REST API стал решающим аргументом в пользу Ollama.

Выбор модели. Ограничение жёсткое — 6 ГБ видеопамяти ноутбучной RTX 3060. Рассматривал llama3.2:3b (слабовата в русском языке), mistral 7b в 4-битном квантовании (влезает впритык и вытесняется в оперативную память, когда видеопамять нужна кому-то ещё), gemma2:2b (быстрая, но хуже следует формату) и qwen2.5:3b (1.9 ГБ на диске, приличный русский, хорошо слушается системных промптов). Выбрал qwen2.5:3b как компромисс между качеством русского языка, скоростью и запасом видеопамяти.

Настройка модели под роль. Полноценное дообучение весов (fine-tuning, LoRA) на 6 ГБ технически возможно, но для этой задачи избыточно: модель не нужно учить новым знаниям, нужно закрепить поведение — роль синоптика, формат ответа, правила принятия решений. В Ollama для этого есть механизм Modelfile: поверх базовых весов фиксируются системный промпт, few-shot примеры диалога (инструкция MESSAGE) и параметры генерации, из чего командой ollama create собирается новая именованная модель. Приложение обращается к модели meteo-sovetnik как к обычной и ничего не знает про промпты.

Принуждение к формату. Есть три уровня строгости: просьба в промпте («отвечай только JSON» — работает через раз), режим format=json в Ollama (гарантирует валидный JSON, но не структуру) и structured outputs — передача полной JSON-схемы, по которой движок ограничивает генерацию прямо на уровне токенов. Использовал третий, самый строгий вариант: схема с обязательными полями и типами передаётся в каждом запросе, и модель физически не может ответить мимо неё.

3. Описание моделей

Приложение собрано из трёх модулей Python (Flask) плюс специализированная модель в Ollama.

weather.py — клиент Open-Meteo. Геокодинг превращает название города в координаты и страну, прогноз забирает текущую погоду (температура, ощущаемая температура, влажность, ветер с порывами, код погоды) и суточные показатели (минимум/максимум температуры, вероятность и сумма осадков, максимальный ветер, УФ-индекс). Коды погоды WMO переводятся в русские описания словарём. Серверов прогноза два — основной api.open-meteo.com и резервный historical-forecast-api.open-meteo.com с тем же API: выяснилось, что в некоторых сетях основной домен не резолвится. Список перебирается с таймаутом 6 секунд в два прохода, рабочий сервер запоминается и переставляется в начало списка, чтобы не ждать таймаут на каждом запросе.

Модель meteo-sovetnik — специализация qwen2.5:3b через Modelfile. В системном промпте: роль синоптика-консультанта, ответ только по-русски и обычными словами, 3–5 конкретных позиций одежды без нижнего белья и без зонта в списке, правило про зонт (вероятность осадков больше 40% или сумма больше 1 мм), поправки на ветер (при порывах от 40 км/ч зонт бесполезен — советовать капюшон) и УФ-индекс (от 6 — крем и головной убор), целочисленный индекс комфорта от 1 до 10. Двумя MESSAGE-парами зашиты эталонные ответы для контрастных ситуаций — тёплый ясный день и холодный ливень с ветром; температура генерации 0.3.

advisor.py — клиент Ollama. В запрос уходит человекочитаемая сводка погоды, параметр format с JSON-схемой (обязательные поля summary, clothing[], umbrella, umbrella_reason, tips[], comfort 1–10) и keep_alive=2h, чтобы модель не выгружалась из видеопамяти между запросами. Ответ дополнительно валидируется кодом: решение про зонт сверяется с тем же детерминированным правилом, что зашито в промпт, длина summary — не короче четырёх слов, каждый пункт одежды — против фильтра стоп-слов и длины. Если проверка не прошла, запрос повторяется с температурой 0.1; если модель ошибается и во второй раз, булево решение про зонт принимает правило (с причиной, собранной из данных прогноза), а бракованные пункты одежды выбрасываются из списка. При старте приложения модель греется фоновым запросом, чтобы первый пользователь не ждал загрузку весов.

app.py и интерфейс. Два маршрута: страница и GET /api/advice?city=... с JSON-ответом и внятными кодами ошибок (город не найден — 404, сервис погоды или модель недоступны — 502 с текстом для пользователя). Страница — тёмная карточная вёрстка без фреймворков: слева фактическая погода с диапазоном температур и шкалой индекса комфорта, справа совет модели — краткая сводка, бейдж про зонт с причиной, список одежды по слоям и практические советы; на время запроса крутится спиннер с предупреждением, что первый запрос дольше. Приложение собирается в автономный weather_advisor.exe (PyInstaller, шаблоны упакованы внутрь), так что для показа достаточно Ollama и одного exe-файла.

4. Гипотеза

Основная гипотеза: локальной модели в 3 миллиарда параметров на ноутбучной видеокарте с 6 ГБ памяти достаточно, чтобы стабильно выдавать полезный структурированный совет по погоде — при условии, что вокруг модели выстроена страхующая обвязка: специализация через Modelfile с few-shot примерами, принуждение к формату на уровне движка генерации и программная валидация ответа с повторными запросами и детерминированным правилом для критичного решения про зонт.

Частные предположения: structured outputs полностью снимут проблему невалидного JSON; без few-shot примеров и валидации модель будет периодически ошибаться в булевом решении про зонт и вставлять в список одежды неуместные пункты; после прогрева ответ уложится в интерактивные 5–10 секунд на моей видеокарте.

5. План исследования

1. Развернуть Ollama, выбрать и скачать базовую модель под ограничение 6 ГБ видеопамяти.
2. Собрать специализированную модель meteo-sovetnik через Modelfile.
3. Написать клиент Open-Meteo (геокодинг и прогноз) и клиент Ollama со structured outputs.
4. Собрать веб-приложение на Flask с карточным интерфейсом и упаковать его в exe.
5. Провести испытания: замерить время этапов на холодном и тёплом старте, проверить решение про зонт на городах с контрастной погодой, оценить качество текстов совета.
6. По итогам доработать модель (few-shot) и обвязку (валидация, фильтры), повторить замеры.
7. Оценить рынок бесплатных ИИ-ассистентов по опыту их использования в работе.

6. План эксперимента

Стенд: ноутбук с видеокартой RTX 3060 Laptop (6 ГБ), 32 ГБ ОЗУ, Windows 11; Ollama 0.31 нативно; код на Python 3.14 (Flask, requests). Базовая модель qwen2.5:3b занимает 1.9 ГБ на диске и около 2.2 ГБ в видеопамяти вместе с контекстом.

Замеры времени: по этапам (геокодинг, прогноз, генерация совета) отдельно для холодного старта, когда весов ещё нет в видеопамяти, и для тёплого. Часть замеров снята в университетской сети, где основной сервер прогноза недоступен — это даёт честную оценку работы резервной схемы.

Проверка качества: запросы по городам с контрастной погодой (Ульяновск, Санкт-Петербург, Мурманск, Сочи, Казань); решение модели про зонт сверяется с детерминированным правилом по данным прогноза; списки одежды и советы оцениваются глазами на предмет абсурдных пунктов и несуществующих слов — до и после доработки модели few-shot примерами.

7. Реализация эксперимента

7.1. Развёртывание и первые запуски

Ollama поднялась без приключений, докачка qwen2.5:3b заняла несколько минут, сборка meteo-sovetnik командой ollama create — секунды: веса не копируются, к ним привязывается новый системный промпт и параметры.

Первый сюрприз пришёл из сети: в университетской сети не резолвится домен api.open-meteo.com — DNS-сервер отвечает отказом (Query refused), при этом соседний geocoding-api.open-meteo.com работает. Разобрался через DNS-over-HTTPS: домен жив, адрес выдаётся, просто локальный резолвер его режет. Помог резервный сервер проекта historical-forecast-api.open-meteo.com с тем же API: добавил в клиент список серверов с перебором и «липким» выбором рабочего. Первый запрос в такой сети тратит 6 секунд на таймаут основного сервера, все последующие идут сразу в резервный за 0.5–2 секунды. В домашней сети работает основной сервер без задержек.

Второй сюрприз — холодный старт: самый первый запрос к модели занял 59 секунд, пока Ollama поднимала веса в видеопамять, и со стороны это выглядело как зависание приложения. Вылечено тремя мелочами: фоновый прогрев модели при старте приложения, keep_alive=2h, чтобы модель не выгружалась между запросами, и честное предупреждение в интерфейсе. Тёплый запрос совета укладывается в 4–10 секунд, полный ответ пользователю — в 5–12.

7.2. Качество советов и доработка модели

Третий — и самый интересный — слой проблем: качество генерации. Structured outputs отработали идеально в узком смысле: за все прогоны ни одной ошибки разбора JSON, все обязательные поля на месте, comfort всегда целое в диапазоне. Но схема не гарантирует здравый смысл внутри полей. Модель периодически выдавала «зонт: брать» при нулевой вероятности осадков (и однажды — с обоснованием «вероятность осадков 0%, но зонт всё равно не нужен» внутри поля причины при umbrella=true), а в списке одежды у неё встречались «базовые трусики или носки», «зонт не нужен» как предмет гардероба и несуществующее слово «припартируй» в советах.

Лечение шло в два приёма. Сначала few-shot: в Modelfile добавлены два эталонных диалога — тёплый ясный день и холодный ливень — с образцовыми списками одежды и формулировками; температура снижена до 0.3. Затем валидация в коде: решение про зонт сверяется с детерминированным правилом по данным прогноза, summary — не короче четырёх слов, пункты одежды — против фильтра стоп-слов (бельё, зонт и т.п.) и длины; при провале — повторный запрос с температурой 0.1, при повторном провале булево решение принимает правило, а бракованные пункты выбрасываются. Попутно нашёл у себя ошибку: функция проверки списка одежды применялась и к списку целиком, и к отдельному пункту, а в ней стояло требование «от 2 до 6 элементов» — одиночный пункт никогда не проходил, и фильтр молча выкашивал весь список до заглушки «одежда по сезону». Разнёс проверки на два уровня — пункт и список.

После доработки прогнал контрольную серию по пяти городам с контрастной погодой (таблица 2): решение про зонт совпало с правилом во всех случаях, включая Санкт-Петербург со 100% вероятностью осадков, абсурдных пунктов в одежде не осталось. Остаточные дефекты — редкие падежные рассогласования вида «непромокаемые обувь» и «кроссовок»; на них 3b-модель, честно говоря, право имеет, на смысл советов они не влияют. Это осознанный инженерный выбор, а не упрощение: LoRA на 6 ГБ видеопамяти учится часами, воспроизводится плохо, а выигрыша для задачи такого размера не даёт.

8. Оценка рынка бесплатных ИИ-ассистентов

Всю работу — код, отладку и этот отчёт — я делал в связке с бесплатным ИИ-ассистентом (Claude, модель уровня Sonnet в бесплатном тарифе), поэтому оценка рынка ниже опирается на живой опыт, а не на чужие обзоры.

Бесплатный сегмент к 2026 году выглядит так. Универсальные чат-ассистенты: ChatGPT, Claude, Gemini, DeepSeek, Qwen Chat — у всех есть бесплатный доступ к моделям среднего класса с дневными лимитами; российские GigaChat и YandexGPT тоже бесплатны для персонального использования, но в кодинге заметно слабее лидеров. Инструменты в редакторе: GitHub Copilot и Windsurf имеют бесплатные тарифы с ограниченным числом автодополнений и агентных запросов. Отдельный класс — полностью бесплатные локальные модели через Ollama или LM Studio: qwen, llama, deepseek-r1 в младших размерах; лимитов нет вообще, но, как показала эта работа, любой их вывод нужно проверять кодом.

Что бесплатные ассистенты закрывают уверенно: типовой прикладной код (клиенты API, Flask-приложения, скрипты на 100–300 строк), вёрстку интерфейсов, конфигурацию инструментов, объяснение чужого кода и ошибок. Практически весь код этого задания — ровно такого класса, и ассистент выдавал рабочие версии с первой-второй попытки.

Где граница проходит на практике. Первое — редкие и свежие тонкости инфраструктуры: сетевую блокировку DNS в конкретной сети или поведение конкретной версии инструмента ассистент не «знает», помогают только эксперимент и чтение логов. Второе — лимиты: на бесплатных тарифах длинная отладочная сессия упирается в квоту в самый неподходящий момент. Третье — большие кодовые базы: без платных агентных режимов с индексацией проекта ассистент видит только те файлы, что ему показали. Четвёртое — ответственность: модель охотно выдаёт правдоподобные, но неверные детали (мы это видели даже у 3b-модели с её «припартируй»), поэтому слепое копирование без прогона недопустимо.

Итоговая оценка: для учебных, типовых и прототипных задач бесплатного сегмента сегодня достаточно с запасом — связка «бесплатный облачный ассистент для разработки + бесплатная локальная модель внутри продукта» закрыла это задание целиком, от кода до отчёта. Платные тарифы покупают не «ум», а объём: большие лимиты, большой контекст, агентные режимы на всём проекте.

9. Вывод

Гипотеза подтвердилась: локальной модели на 3 миллиарда параметров хватило для полезного погодного советника, но ключевое слово — обвязка. В чистом виде qwen2.5:3b выдавала то зонт при нулевых осадках, то трусики в списке одежды. Рабочим приложение сделали три приёма: специализация модели через Modelfile с few-shot примерами, принуждение к формату через JSON-схему на уровне движка (ни одной ошибки разбора за все прогоны) и программная валидация с повторным запросом и детерминированным правилом для решения про зонт. После этого контрольная серия по пяти городам прошла без единой смысловой ошибки.

Из технических уроков: холодный старт локальной модели (минута на загрузку весов) обязан быть спрятан от пользователя прогревом и keep_alive; у публичных API полезно иметь резервный сервер — в университетской сети основной домен Open-Meteo просто не резолвится; и валидатор тоже надо тестировать — моя собственная проверка списка одежды однажды молча выкосила весь список.

Практический выход: работающее веб-приложение, собранное и в автономный exe, Modelfile модели, скрипты сборки и запуска, отчёт. Всё крутится локально, наружу уходят только запросы за прогнозом. По рынку бесплатных ИИ вывод простой: связка бесплатного облачного ассистента для разработки и бесплатной локальной модели внутри продукта уже закрывает задачи такого класса целиком; ограничения бесплатного сегмента — лимиты, слепые зоны по свежим тонкостям и необходимость проверять каждый вывод — обходятся организацией процесса, а не деньгами.
